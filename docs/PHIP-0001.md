## Abstract

PHIP-0001 proposes a durable, community-managed identity mapping between the native PS5 homebrew title identifier (`title_id`) and a separate, globally structured identifier (`app_id`). It defines a simple registration document, transparent review, deterministic indexes, and best practices for participating installers.

## Motivation and scope

Native PS5 homebrew frequently uses `PPSA12345`-like title identifiers and installation paths such as `/data/homebrew/PPSA12345/`. Independently authored applications might reuse identifiers accidentally. Such reuse can cause incorrect listing, unexpected upgrades or overwrites and ambiguous save-data ownership.

This proposal applies to **native PS5 homebrew titles**, not ELF payloads without installed title identifiers, official Sony registration, firmware, package signing, or a universal right to any numeric namespace.

## Normative terminology

**MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** describe requirements *for participants electing to implement PHIP-0001*. They impose no requirements on unaffiliated tools or publishers.

### Identifiers

* A record **MUST** have exactly one `title_id` matching `^PPSA[0-9]{5}$`, excluding the template placeholder `PPSA99999`.
* A record **MUST** have a `app_id` matching `io.github.<owner>.<slug>`, with lowercase components and the `owner` component equal to the recorded GitHub owner, compared case-insensitively.
* Both `title_id` and `app_id` **MUST** be unique within the approved PHIP registry.
* Neither field **SHOULD** be changed for the same application. Renames and ownership changes need maintainer-mediated migration procedures.
* Developers **SHOULD** check established external community registries before requesting a number. Local uniqueness is **not** global uniqueness across every PS5 title or catalog.
* These identifiers are informational; they are **not cryptographic certificates or proof of ownership**.

### Registration record

A registration **MUST** be a UTF-8 JSON object stored at `registry/<TITLE_ID>.json`. Its required fields:

| Key | Meaning |
| --- | --- |
| `schema_version` | Literal `1.0` |
| `title_id` | Stable PS5 homebrew title identifier |
| `app_id` | Stable global identity in the PHIP namespace |
| `name` | Human-readable application name |
| `developer` | Human-readable publisher credit |
| `owner` | GitHub account/organization that owns the app repo |
| `source_repo` | HTTPS `https://github.com/OWNER/REPO` URL |
| `status` | `reserved` or `registered` |
| `created` | ISO 8601 calendar date `YYYY-MM-DD` |

Optional: `description` and `license`. Extra keys are not allowed under schema 1.0. See [JSON Schema](../schemas/registration.schema.json).

A `reserved` record documents the intent to use a title. A `registered` record identifies an existing project; the registry does not download, execute, sign, or certify its releases.

### Submission, review and ownership

New requests **SHOULD** be submitted in individual pull requests by the account matching `owner`. Automation checks local uniqueness and that the author login matches this owner on PR changes. Maintainers **MUST** independently assess whether the submitter controls the linked source repository and review evidence of any external collisions. The PR author check is necessary but **not sufficient** proof of source ownership (in particular for organization repositories, compromised accounts or transferred ownership).

Already accepted immutable fields **MUST NOT** be modified silently. Transfer requests, abandoned projects, conflict appeals and disputes require a separately documented manual review. The current automation blocks such changes by default. Status, name, description and license updates may proceed under review.

A maintainer acceptance binds the proposed identity only **within this PHIP community registry**. External projects can reject this proposal, and official platform allocations have precedence over unofficial conventions where applicable.

### Index and stores

After approval, deterministic tools build `index/registry.json` and `index/stats.json`. Clients **SHOULD** use `title_id` as a *candidate* lookup key and compare `app_id`, source/publisher metadata, and installed information before updating or replacing software. Clients **MUST NOT** treat a matching `title_id` alone as permission to overwrite a different publisher's files.

Registrations are not manifests of installed ZIP contents. Stores **SHOULD** separately verify artifact hashes, metadata versioning, publisher trust, and installation path handling.

### Example

```json
{
  "schema_version": "1.0",
  "title_id": "PPSA12345",
  "app_id": "io.github.exampledev.example-app",
  "name": "Example Homebrew App",
  "developer": "Example Developer",
  "owner": "exampledev",
  "source_repo": "https://github.com/exampledev/example-app",
  "status": "reserved",
  "created": "2026-10-13"
}
```

**This example is not a reservation.**

## Compatibility and future work

PHIP-0001 does not redefine `sce_sys/param.json`, FSELF binaries, Sony Title ID rules or a ZIP file layout. Follow-on proposals may cover build manifests, update APIs, signing, and migration conventions. Establishing links or coordination with existing PS5 homebrew title registries remains a community governance objective.

## Security and privacy

See [SECURITY.md](SECURITY.md). Metadata cannot establish legal ownership, content safety, or exclusive global ID allocation. The repository stores public project data and does not need user credentials.

## Governance / status

This document is a **draft**, not an adopted scene-wide standard. Changes are discussed through issues and PRs. Compatibility breaking schema changes require a new documented version and a migration path. There is no claim of affiliation with Sony, PlayStation, or any other company.
